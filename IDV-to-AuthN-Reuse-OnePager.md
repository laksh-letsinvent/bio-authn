# Biometric AuthN: The Case for Reusing the Existing IDV Stack

---

## Context

When extending a verified identity into a step-up authentication capability, the natural question is whether to build on the existing Identity Document Verification (IDV) stack or procure a separate biometric authentication solution. This one-pager sets out why reuse is the stronger default, and what specifically carries over.

---

## What Already Exists in the IDV Stack

A full IDV flow — selfie capture, liveness detection, face-to-document matching — produces three reusable artefacts before a single line of auth code is written:

- A **liveness-verified selfie** captured via a certified mobile SDK
- A **face embedding** generated by a production-grade recognition model
- A **certified liveness decision** backed by ISO 30107-3 / iBeta PAD testing

All three are the inputs an authentication flow needs. The IDV flow already ran them.

---

## SDK Reuse

The mobile capture SDK is already integrated, reviewed, and shipping. Adding a biometric auth capture flow is a configuration change, not a new SDK dependency. There is no additional bundle review, no new third-party security assessment, no incremental integration cycle. The liveness challenge the user sees at step-up is the same one they passed at onboarding.

---

## Enrolled Template Without an Enrollment Step

The face embedding generated during IDV becomes the biometric reference for authentication. There is no separate enrollment event, no additional user-facing flow, no re-capture campaign. The customer already enrolled — they just don't know they did. This is a structural advantage a greenfield auth solution cannot replicate without running its own onboarding capture.

---

## Liveness Certification Carries Over

Liveness certification (ISO 30107-3 PAD, iBeta Level 1/2) is expensive, time-consuming, and tied to a specific SDK version. The IDV stack already holds this certification. Using the same SDK for auth means the liveness assurance evidence is already on file. A separate auth solution requires re-certification from zero.

---

## Accuracy Governance Owned at Source

The matching engine, threshold curves, FAR/FRR evidence, and demographic fairness data are all properties of the existing IDV solution. For high-stakes step-up operations — where auth accuracy must equal IDV accuracy — the operating threshold is already known, documented, and defensible. The institution's role is vendor oversight, not biometric science. A new vendor resets this clock entirely.

---

## Vendor Governance Already Complete

Due diligence, data processing agreements, DPIA, security assessments, pen test results, and contractual SLAs are already in place. Extending scope to authentication is typically a contract amendment. A new vendor triggers the full procurement and legal cycle — realistically 3–6 months in a regulated environment.

---

## Single Audit Surface

One vendor means one set of data retention policies, one breach notification pathway, one Article 28 controller-processor relationship, one point of accountability for biometric data handling. Splitting IDV and auth across separate vendors doubles the supply chain complexity and the regulatory reporting surface.

---

## Template Architecture: Bank-Side Retention

The face embedding and raw selfie are retained by the institution, not the IDV vendor. This provides:

- **Vendor independence** — the comparison asset is yours, not a vendor-locked record
- **Model version resilience** — raw selfie enables re-processing through an updated recognition model without customer re-enrollment
- **Audit evidence** — raw selfie supports dispute resolution in fraud cases; a similarity score does not

The comparison at auth time is delegated back to the existing vendor (new selfie in, match decision out), keeping accuracy governance and certification liability with the party best placed to hold it.

---

## What the Institution Owns

Reuse does not mean zero governance responsibility. The institution retains:

- **Threshold selection** — vendor provides accuracy curves; institution chooses the operating point and documents the rationale
- **Retry and lockout policy** — number of permitted attempts before step-up is denied
- **Fairness monitoring** — periodic audit of false rejection rates across demographic cohorts against the actual customer population
- **Purpose and consent** — biometric use for authentication is a new processing purpose; privacy notice and legal basis must be updated regardless of vendor

---

## What a New Vendor Would Cost

| Dimension | Reuse Existing Stack | New Vendor |
|---|---|---|
| SDK integration | Config change | Full integration + review |
| Biometric enrollment | Already done at IDV | Separate user-facing event |
| Liveness certification | Already on file | Re-certify from zero |
| Vendor governance | Amendment | Full procurement cycle |
| Accuracy evidence | Available now | Build from scratch |
| Audit surface | Single vendor | Two parallel supply chains |

---

## Bottom Line

Every component a biometric auth flow needs — liveness, capture, embedding, matching, certification, governance — already exists in the IDV stack. Reuse is not the path of least resistance; it is the architecturally sound choice. A separate vendor purchases duplication of cost, governance burden, and integration complexity without a commensurate gain in capability.
